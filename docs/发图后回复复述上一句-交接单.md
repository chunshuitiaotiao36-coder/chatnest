## 🎯 2026-09-03 真凶找到了：模型从头到尾没复述过，是前端把上一条画上去的

`index.html` 的 `recoverAfterBreak()`——流一断就去库里捞回复填进当前气泡：

```js
const last=[...list].reverse().find(m=>m.role==='assistant');   // 老写法
if(!last||!(last.text||'').trim())throw 0;
msg.text(last.text); msg.finish();
```

**捞的是「整个会话最后一条助手消息」，一个字都不检查它属不属于这一轮。**
于是这一轮但凡没落库（`/api/chat` 报错、流当场断），它就把**上一轮的回复原样画进
新气泡**，还 `msg.finish()` 装成正常收尾。

### 对得上这份单子里的每一条

| 现象 | 老解释 | 真解释 |
|---|---|---|
| 「与上一轮回复**逐字相同**」 | 模型重放 | 前端 `msg.text(上一条)`，**逐字相同才是它的指纹**——模型重说不会一个字节不差 |
| 「退出对话再进来就没有这两条」 | 没定位 | 压根没落库，本来就什么都没有 |
| Thought process 正常、Read 也调了 | 说明 prompt 没问题 | 确实没问题：模型开始跑了，是**这一轮的连接断在中途** |

⇒ **「复述」不是一个 bug，是失败的伪装。** 这份单子的「待查」三条
（`stop_reason` / `resume` 回退 / base64 体积）追的是一个不存在的模型行为，
方向从一开始就偏了。真正要查的是「`/api/chat` 那一轮为什么断」。

### 已修（两处）

1. **`recoverAfterBreak` 只认比这一轮用户消息更新的那条回复。**
   判据用 `userRow.dataset.msgId`（由 `conversation` 帧写入）：
   连它都没有 = 这一轮连用户消息都没落库 = 没什么可捞的，老老实实 `msg.fail()`。
   真·网络中断但后端已经写完的那种情况不受影响——那时 `id` 一定更大，照常捞回来。
2. **`/api/chat` 非 2xx 时把状态码带出来**：`「请求失败（HTTP 500）」`。
   原来只有一句「请求失败」，她截图给我也分不出 4xx 还是 5xx。

### 下一步：现在它会说实话了

修之前，失败长得跟成功一模一样（一条以假乱真的回复），所以没人知道有多少轮其实断了。
修之后，断掉的那一轮**气泡里直接是错误文案 + HTTP 状态码**。

她 09-03 报的新症状「发图片就转两下然后回滚变成上一条消息，退出再进来两条都没了」
就是这条路径，而且是每次都触发——说明 `/api/chat` 在带图那一轮**快速失败**。
**下次复现，把气泡里那行错误连状态码一起发我**，比服务器日志还快。
`claude.py` 里的 `turn_resume` 打点同时也在了。

## 待查（需要服务器日志，我这边看不到）

复现后查那一轮的：

1. **`stop_reason` 与 `num_turns`** —— `actor.py` 的 `ResultMessage` 分支已经在打
   `cache_usage model=… stop=… turns=… text=… input=… cache_create=… cache_read=… cost=…`
   （`cache_logger`）。看 `stop=` 是不是 `max_turns` / 异常值，`text=` 是不是 false
   （first_text_token_seen——若为 false 说明这一轮**根本没吐过正文 token**）。
2. **`resume=session_id` 这条路**（`claude.py:704`）。若 session 恢复异常，
   模型可能重放上一轮的输出。重点比对：复述那一轮传入的 `resume` 值，
   与上一轮的 `session_id` 是否指向同一段、是否发生过回退。
3. **Read 返回的 base64 体积**。IMG_4615 是手机原图，几 MB 很正常，
   base64 后更大。若单条工具结果撑爆了单轮预算，可能出现「调完工具就没话说了」。
   修好显示后，工具详情那一格会直接写出约多少 KB，先看这个数。
4. 若以上都正常，则怀疑落在 CLI 侧：同一 session 内 image block 进入历史后的
   重放行为。
