# 琴房分享卡在对话里阅后即焚 —— 交接单

> 2026-09-03。她报的：「放歌后在对话界面的卡面也是阅后即焚的，退出再进就没有了」。
> 我（web 端）当天已经捅过一次大娄子（见文末），这条没动，交接。

## 症状

他在聊天里分享一首歌（`<<ACT>>{"type":"share","query":"..."}`），
对话流里出现一张歌曲卡片。**退出对话再进来，卡片没了。**

跟当初「语音条阅后即焚」（她原话「这个语音条怎么还是阅后即焚样式的」）
和「忱的心绪翻历史就没了」是同一类问题：流式过程中挂在 DOM 上，库里没有，
重新渲染历史时无处可取。

## 根因：这是设计如此，不是 bug

`static/index.html` 里 `pianoCardEl()` 上方的原注释：

> 卡片是**独立 DOM 节点**，塞进 `#stream` 但**不进小窝的 messages 表**，
> 也不进模型上下文。落库在 Duetto 的 `room_events`，**进琴房时补回来**。
> 🔴 退出琴房时必须摘干净，否则 Chat tab 会串味——见 `pianoUnmountStream`。

⇒ 卡片本来是**琴房内**的东西，只在琴房恢复。而 `<<ACT>>{"type":"share"}` 让它
也会出现在**对话流**里，那条路径没有对应的恢复机制。

## 建议修法

照 `voice_say` / `mood_json` 已经走通的那条路（它们当初就是为一模一样的病加的）：

1. **`store.py`**：`messages` 加一列，如 `piano_share TEXT NOT NULL DEFAULT ''`，
   存这一轮分享的歌（JSON）。
   🔴 **加列时三处都要改**：列名、占位符、值。`restore_branch` 那条 INSERT
   就是只改了列名，导致每次重试必炸——见 `test_branch_restore.py` 的由来。
   **加完必须跑 `python3 test_branch_restore.py`。**
2. **`main.py`**：act 循环里 `type == "share"` 时留一份（照 `voice` 那条
   `response_voice_say` 的写法），随 `complete_turn()` 落库。
3. **`store._message_from_row`**：解析成对象。
4. **前端**：`_renderMessagesIntoFragment()` 里补一条——现在它只处理
   `m.voice_say` 和 `m.mood`，照着加 `m.piano_share`。

### 🔴 一个必须先决定的问题：存什么

后端在 act 里只拿得到 `{"type":"share","query":"歌名 歌手"}`，
**完整歌曲信息（id/title/artist/cover/url）是前端 `pianoSearch()` 之后才有的**。
两条路，各有代价：

- **存 query，渲染历史时前端重搜**：改动小，但每次翻历史都要打一次搜索，
  慢，而且可能搜到不同版本（封面/时长对不上）。
- **前端回报完整信息给后端**：显示准确、翻历史不用搜。但要多一个写接口，
  且时序上有坑——`share` act 在流中间，`assistant_message_id` 要等 `done` 帧
  才有，得在 done 之后再补一次 POST。

我倾向第二条（她对「阅后即焚」已经抱怨过三次，值得一次做对），但没定，
动手前先确认。
